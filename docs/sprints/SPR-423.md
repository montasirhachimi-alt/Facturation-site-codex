# SPR-423 — Procurement Operational Workspace

## Summary

SPR-423 transforms Procurement from a technical foundation into an operational purchasing workspace.

Administrators can now manage the visible purchasing lifecycle:

Supplier -> Purchase Order -> Goods Receipt -> Inventory Update

The implementation reuses the existing Procurement persistence layer, Product Catalog, Inventory posting engine and module activation system.

## What Changed

- Supplier workspace now includes search, status filtering, active/archive badges, create/edit dialogs and Supplier detail pages.
- Purchase Orders now expose operational actions: view, edit draft, confirm, receive, duplicate, cancel and delete draft.
- Purchase Order detail pages show header context, supplier, dates, reference, notes, lines, totals, receipt progress and related receipts.
- Goods Receipt creation is restricted to confirmed or partially received Purchase Orders.
- Posted Goods Receipts continue to create Inventory `RECEIPT` movements through the existing transaction-safe Inventory posting engine.
- Procurement is now active in the default `alpha.crm-sales` profile alongside Product Catalog and Inventory.
- Dashboard now includes a compact Procurement section for draft orders, orders awaiting receipt, low-stock purchasing needs and recent receipts.

## Architecture

Procurement remains modular:

```text
Procurement UI
  -> Procurement local service/cache
  -> /api/persistence/procurement
  -> Procurement repository
  -> Inventory posting engine for posted Goods Receipts
```

No Inventory logic was duplicated in Procurement UI.

## Supplier Workspace

Supported visible fields:

- company name
- contact / trade name
- phone
- email
- address
- VAT
- notes
- status

The existing `tradeName` field is used as the visible contact / trade-name field to avoid a schema change.

## Purchase Order Lifecycle

Supported statuses:

- Draft
- Confirmed
- Partially Received
- Fully Received
- Cancelled

Operational rules:

- Draft orders can be edited.
- Draft orders can be deleted safely.
- Draft orders can be confirmed.
- Confirmed and partially received orders can receive goods.
- Goods receipts update Purchase Order receipt status through posted quantities.
- Cancelled orders cannot be received.

## Inventory Integration

Goods Receipt posting still uses the existing Inventory repository flow.

Each received line creates an Inventory `RECEIPT` movement with:

- `referenceType = GOODS_RECEIPT`
- the Goods Receipt ID
- the target warehouse
- the received Product quantity

The returned Procurement and Inventory snapshots refresh local UI state immediately.

## Dashboard

The compact Procurement dashboard section shows:

- Draft Purchase Orders
- Orders awaiting receipt
- Low-stock Products needing purchasing
- Recent Goods Receipts

Only one active dashboard contribution renders the Procurement block; other Procurement dashboard metadata remains prepared for future layout expansion.

## Activation

The following modules are now Alpha-ready and active in `alpha.crm-sales`:

- `procurement.overview`
- `procurement.suppliers`
- `procurement.purchase-orders`
- `procurement.goods-receipts`

The legacy hidden purchasing modules remain planned and inactive.

## Runtime Impact

- No Runtime redesign.
- Runtime validation updated to reflect Procurement activation in Alpha.
- Existing module activation, route availability, dashboard contribution and Command Center filtering continue to drive visibility.

## Limitations

- Supplier invoices are not implemented.
- Accounting and payments for suppliers are out of scope.
- Approval workflows are out of scope.
- Multi-currency and tax redesign are out of scope.
- Goods Receipt reversal and returns remain future work.

## SPR-423A — Partial Goods Receipt Line Identity Fix

The Goods Receipt dialog uses line IDs derived from the Purchase Order line while the user prepares a receipt. That is acceptable as transient UI state, but the server persistence layer must not persist that transient ID directly.

The canonical persisted Goods Receipt line ID is now generated by the Procurement repository from:

```text
goodsReceiptId + purchaseOrderLineId + position
```

This preserves the dedicated `purchaseOrderLineId` relation while allowing multiple partial Goods Receipts against the same Purchase Order line.

Example:

- Receipt 1 receives 3 units from PO line A.
- Receipt 2 receives 1 unit from PO line A.
- Receipt 3 receives 2 units from PO line A.

All three persisted Goods Receipt lines have different IDs and all three reference PO line A through `purchaseOrderLineId`.

## SPR-423B — Procurement UX & Usability Polish

SPR-423B improves Procurement clarity without changing Runtime, persistence, Prisma, APIs, database or business rules.

UX improvements:

- Purchase Order line editing now exposes explicit procurement column headers:
  - Produit
  - Description
  - Qté
  - Unité
  - Coût unitaire HT
  - Remise %
  - TVA %
  - Sous-total HT
- Mobile line fields keep visible labels so numeric inputs are never ambiguous.
- Purchase Order totals now render as a structured live summary:
  - Sous-total HT
  - Remise
  - TVA
  - TOTAL TTC
- Purchase Order details now separates Sous-total HT, Remise, TVA, Total TTC and Reception in metric cards.
- Procurement icon-only actions now include clear `aria-label`, `title` tooltips and visible keyboard focus styling.
- Empty tables for Suppliers, Purchase Orders and Goods Receipts now show helpful French messages and next-step guidance.
- Important form fields now include helper text:
  - Livraison prévue
  - Reference fournisseur
  - Remise globale
  - Date de reception
  - Reference de reception
- Procurement button wording was normalized around operational actions:
  - Creer la commande
  - Confirmer
  - Creer une reception
  - Poster la reception
  - Dupliquer
  - Annuler
  - Supprimer

No procurement workflow changed. The polish only improves discoverability, accessibility and first-time-user comprehension.
