# SPR-442 — Employee Administrative File, Document Templates & Onboarding V1

## Summary

SPR-442 completes the Alpha-grade HR administrative experience by adding a canonical employee dossier with HR document types, reusable HR templates, generated employee documents, signed/final upload metadata and onboarding readiness.

No payroll, CNSS/IR, e-signature provider, generic enterprise DMS, OCR, AI drafting, recruitment, performance management or workflow engine was introduced.

## Repository Reconciliation

Existing foundations:

- legacy `HrDocument` exists but belongs to payroll-era `Employee`, not canonical `HrEmployee`;
- legacy `Document` is commercial Sales/Purchasing-era infrastructure and is not suitable for HR personnel files;
- Sales PDF and preview utilities exist, but official HR template truth now lives in deterministic HR service generation rather than client-side rendering;
- there is no generic attachment/storage service in the active architecture;
- `Company` provides name, address, email and phone fields suitable for template variables;
- canonical `HrEmployee`, `HrDepartment`, `HrPosition` and `HrEmploymentContract` contain enough Alpha fields for contract/document generation;
- `/api/persistence/hr`, `hr-repository` and `HrPersistenceProvider` are the existing tenant-scoped HR persistence bridge.

## Reuse / Extend Decisions

| Foundation | Decision | Rationale |
| --- | --- | --- |
| Canonical `Hr*` HR family | Extend | Employee dossiers belong to the active HR source of truth. |
| Legacy `HrDocument` | Leave legacy isolated | It references payroll-era `Employee`, not canonical `HrEmployee`. |
| Legacy commercial `Document` | Leave legacy isolated | It represents commercial documents, not HR personnel files. |
| Sales PDF utilities | Reuse conceptually, not as authority | Client/PDF rendering can follow later; official generated text is service-owned. |
| Generic file storage | Introduce minimal HR metadata | No active storage service exists; V1 stores safe references and metadata only. |
| `/rh` workspace | Extend | No second HR application was introduced. |

## Architecture

SPR-442 adds three canonical tenant-scoped Prisma models:

- `HrDocumentType`;
- `HrDocumentTemplate`;
- `HrEmployeeDocument`.

The operational chain is:

```text
Employee
  -> Administrative Dossier
  -> Required Document
  -> HR Template
  -> Generated Document Snapshot
  -> Signed / Final Upload Metadata
  -> Onboarding Readiness
```

Generated document content is persisted on `HrEmployeeDocument.generatedContent` so later template edits do not mutate historical generated employee documents.

## Document Types

HR document types support:

- code;
- name;
- category;
- active flag;
- required-by-default flag;
- optional description.

The taxonomy is configurable and not hardcoded to Moroccan legal compliance. Alpha examples include contract, position sheet, identity, RIB, diploma, confidentiality, internal rules, certificate, signed document, proof and other.

## Templates

HR templates support deterministic `plain_text` rendering only.

Unknown variables are rejected explicitly. Templates containing unsafe script-like content are rejected at the server persistence boundary.

Supported variables:

```text
employee.firstName
employee.lastName
employee.displayName
employee.employeeNumber
employee.email
employee.phone
employee.hireDate
department.name
position.name
manager.displayName
contract.type
contract.startDate
contract.endDate
contract.title
contract.workingTimeType
company.name
company.address
company.email
company.phone
```

## Generated Document Lifecycle

Supported statuses:

```text
missing
generated
awaiting_signature
signed
uploaded
expired
archived
```

A generated document does not automatically count as signed/final. Signed/final completion requires upload metadata.

## Signed / Final Upload

SPR-442 does not upload binary content to a storage provider. It records safe metadata:

- storage reference;
- safe filename;
- MIME type;
- size;
- uploaded timestamp;
- finalization timestamp when marked signed/final.

Supported Alpha formats are PDF, PNG and JPG. Raw binary data is not stored in Prisma.

## Onboarding Checklist

The employee dossier summary reports:

- profile completeness;
- department assignment;
- position assignment;
- active contract;
- required document count;
- complete document count;
- missing document count;
- expired document count;
- completion percentage;
- readiness status.

Expired required documents block readiness.

## UI

The existing `/rh` workspace now includes a `Documents` tab. The employee detail card includes a concise `Dossier administratif` metric.

The Documents tab supports:

- creating document types;
- creating HR templates;
- adding employee-specific required documents;
- generating employee documents;
- recording signed/final upload metadata;
- viewing dossier/document status.

## Tenant Isolation and Security

All records are tenant-scoped through `tenantCompanyId`.

Repository persistence validates ownership for:

- employee;
- document type;
- template;
- employee document;
- contract.

The repository rejects unsafe storage references, unsupported MIME types, oversized metadata and unsafe template content. Document content is not logged.

## Known Limitations

- No binary object storage provider is implemented.
- No PDF rendering/download pipeline for HR generated content is implemented yet.
- No e-signature provider integration.
- No legal template pack or legal advice.
- No employee self-service upload portal.
- No upload from the user's device.
- No automatic extraction of filename, MIME type or file size.
- No secure employee-document archive.
- No notifications/reminders for expiry.
- No full document versioning.
