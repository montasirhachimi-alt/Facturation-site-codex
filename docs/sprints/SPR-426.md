## Sales Order Draft Edit Policy

Sales Orders follow a strict Alpha lifecycle:

1. New Sales Orders must be created as `draft`.
2. Existing Sales Orders may be edited only while persisted status is `draft`.
3. Confirmation and reservation must use the dedicated Sales Order confirmation action.
4. Draft persistence rejects any line that carries committed reservation, delivery or warehouse state.
5. Once confirmed, reserved, partially delivered, delivered, cancelled or archived, the Sales Order cannot be changed through the generic draft edit path.

This policy is enforced in `src/server/persistence/crm-sales-repository.ts`, not only in the UI.

## Sales Order Hardening

The server persistence path now checks:

- correct Sales Orders workspace ID;
- tenant ownership of existing Sales Orders;
- draft-only create/update state;
- dedicated confirmation flow for non-draft transitions;
- absence of reservation/delivery/warehouse commitments in draft edits;
- Company and Contact tenant ownership;
- accepted source Quote where conversion is used;
- tenant ownership of Product line references;
- one Sales Order per source Quote per tenant.

## Dashboard Contribution Fix

The Dashboard now has a real renderer for these Sales Operations contribution keys:

- `dashboard.sales.orders-to-confirm`;
- `dashboard.sales.orders-reserved`;
- `dashboard.sales.deliveries-to-prepare`;
- `dashboard.sales.shipments` remained already rendered.

The renderer is intentionally compact and contribution-driven. It is only visible when the owning Sales Operations modules are active.

These contributions remain planned and hidden because they are not ready as stable dashboard surfaces:

- `dashboard.sales.orders-shortage`;
- `dashboard.sales.orders-recent`.

## Authenticated End-to-End QA

Authenticated browser QA remains a required activation gate.

Current blocker:

- the internal `sales-operations` profile exists in `src/platform/editions/edition.profiles.ts`;
- it is not selectable through a runtime environment variable or local configuration switch;
- the current switch remains a manual code change to `defaultForEnvironment`;
- default `alpha.crm-sales` correctly keeps `/sales/orders`, `/sales/delivery-notes` and `/sales/shipments` unavailable.

Because the environment does not expose a safe authenticated runtime profile switch for Sales Operations, SPR-426 does not promote the modules to Alpha.

## Alpha Activation Decision

Decision: **do not activate Sales Operations in `alpha.crm-sales` yet**.

Reason:

- implementation-side blockers were hardened;
- runtime validation passes;
- but the full authenticated end-to-end workflow required for Alpha promotion was not completed.

## Alpha Profile Before / After

Before:

- `alpha.crm-sales` did not include `sales.orders`, `sales.delivery-notes` or `sales.shipments`.
- `sales-operations` included those modules as an internal controlled profile.

After:

- unchanged.
- `alpha.crm-sales` remains the only default profile.
- `sales-operations` remains the controlled internal QA profile.

## Runtime / Activation Impact

No Runtime redesign.

Runtime validation now includes focused checks for:

- Sales Operations remaining inactive in default Alpha;
- Sales Operations activation through the internal profile;
- Sales Operations dashboard render keys;
- draft-only Sales Order persistence policy;
- Product tenant validation for Sales Order line persistence.
