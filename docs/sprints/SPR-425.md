# SPR-425 — Shipment Persistence & Operational Hardening

Status: Completed
Date: 2026-08-13

## Executive Summary

SPR-425 makes Shipments durable and operationally safe.

The SPR-424 Shipment foundation was a logistics UI/service layer only. Shipments could be created in the internal Sales Operations profile, but they were stored in the client/session service and disappeared after refresh or server restart.

SPR-425 adds persistent Shipment models, a tenant-scoped server repository, a persistence API, client hydration, dashboard/search integration and runtime validation while preserving the core logistics rule:

Delivery Notes own physical Inventory `ISSUE` posting. Shipments manage transport only.

## Previous Limitation

Before this sprint:

- Shipments were activation-gated and useful for UI QA.
- No `SalesShipment` Prisma model existed.
- No Shipment repository or persistence API existed.
- Shipment dashboards and search read only the local session service.
- Refresh/restart lost created Shipments.

## Root Cause / Architectural Gap

SPR-424 correctly separated Shipment from Inventory posting, but stopped at the client foundation. The authoritative Shipment source was still the local `shipmentService`, so there was no durable Delivery Note relationship, no server-side duplicate protection and no restart-safe lifecycle state.

## Persistence Model

Added durable models:

- `SalesShipment`
- `SalesShipmentLine`

Persisted fields include:

- Shipment identity and number
- tenant company scope
- workspace
- Delivery Note relation and display number
- Sales Order relation and display number
- CRM Company relation and display name
- optional CRM Contact relation and display name
- delivery address
- carrier
- tracking number
- shipment date
- expected delivery
- delivered timestamp
- status
- notes
- line items
- timestamps

## Delivery Note Relationship

Each Shipment references exactly one posted Sales Delivery Note.

Server persistence validates:

- Delivery Note exists.
- Delivery Note belongs to the authenticated tenant.
- Delivery Note status is `posted`.
- Sales Order, Company and Contact context match the Delivery Note.
- Shipment lines match the posted Delivery Note lines and quantities.

## Shipment Cardinality

SPR-425 chooses one Shipment per Delivery Note for the current operational model.

This is enforced by:

- `deliveryNoteId @unique`
- `@@unique([tenantCompanyId, deliveryNoteId])`
- server-side duplicate lookup before persistence

Future multi-parcel logistics should introduce a child package/parcels model instead of creating multiple top-level Shipments for one Delivery Note.

## Shipment Identity

Durable Shipment identity is server-owned.

The UI may create a temporary local Shipment for immediate workflow continuity, but the repository replaces it with a server-generated durable ID using `randomUUID()`.

Shipment line IDs are also server-owned and scoped to the persisted Shipment ID and line position.

## Lifecycle Rules

Shipment lifecycle remains deterministic:

```text
draft
→ ready
→ shipped
→ in_transit
→ delivered
```

Cancellation is allowed from active in-progress states according to the existing Shipment utility rules.

Server persistence now validates transitions and sets `deliveredAt` when the Shipment becomes delivered.

## Inventory Safety

Shipment persistence does not import Inventory modules and does not create Inventory movements.

Physical stock continues to be decremented only by Delivery Note posting through Inventory `ISSUE` movements.

## Search Impact

Record Search now includes persisted/hydrated Shipments only when `sales.shipments` is active.

The default `alpha.crm-sales` profile remains unchanged, so Shipment results remain hidden from default Alpha users.

## Dashboard Impact

Shipment dashboard widgets now hydrate persisted Shipment data before reading the shared Shipment service.

Dashboard behavior remains activation-gated through the existing Sales Operations profile.

## Runtime / Activation Impact

No activation behavior changed.

- `alpha.crm-sales` remains the only default profile.
- `sales.shipments` remains inactive in default Alpha.
- `sales.shipments` remains available only in the internal `sales-operations` profile.

## Known Limitations

- No carrier API integration.
- No parcel/package split.
- No barcode labels.
- No GPS tracking.
- No email/SMS notification.
- Shipment remains activation-gated in the internal Sales Operations profile.
- Authenticated browser QA requires a Sales Operations runtime profile/session.

## Recommended Next Decision

Before adding carrier integrations, decide whether BOSIACO needs:

1. one Shipment per Delivery Note with optional package lines, or
2. multiple Shipments per Delivery Note for split-carrier logistics.

SPR-425 deliberately chooses the simpler one-to-one model for operational correctness now.
