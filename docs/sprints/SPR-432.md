# SPR-432 — Finance Operations V1

Status: Completed
Date: 2026-08-17
Sprint type: Medium Capability Sprint

## Executive Summary

SPR-432 transforms Accounting from a hidden technical foundation into the first usable Finance Operations capability.

The operational workflow is now:

```text
Account
   ↓
Journal
   ↓
Manual Journal Entry
   ↓
Draft
   ↓
Post
   ↓
General Ledger
   ↓
Trial Balance
```

Finance is now active in the default Alpha profile through the canonical route:

```text
/accounting
```

## Repository Reconciliation

SPR-432 reuses the foundations created in SPR-430 and SPR-431:

- `AccountingAccount`
- `AccountingJournal`
- `AccountingJournalEntry`
- `AccountingJournalEntryLine`
- double-entry posting invariant
- draft/posted lifecycle
- posted-history protection
- tenant-scoped Accounting persistence
- General Ledger read model
- Trial Balance read model
- integer minor-unit Accounting amount utilities

No duplicate Accounting kernel, reporting engine, persistence architecture, tenant system, navigation system or module activation system was created.

## Canonical Finance Route

The canonical Finance Operations route is:

```text
/accounting
```

It renders:

- Vue d'ensemble
- Plan comptable
- Journaux
- Écritures
- Grand livre
- Balance

No competing `/finance` or `/comptabilite` route was introduced.

## Chart of Accounts

The Plan comptable tab supports:

- list accounts;
- search accounts;
- create accounts;
- edit accounts;
- mark accounts active/inactive;
- inspect code, name, type, normal balance and currency.

The UI remains global and country-agnostic. No Moroccan, French, Spanish or other localized chart template was introduced.

## Journals

The Journaux tab supports:

- list journals;
- search journals;
- create journals;
- edit journals;
- inspect code, name, type and status.

Journal types reuse the canonical global SPR-430 types.

## Journal Entries

The Écritures tab supports:

- create a manual journal entry;
- choose journal and accounting date;
- add line descriptions;
- select accounts;
- enter debit and credit amounts;
- add and remove draft lines;
- review total debit, total credit and difference;
- save as draft;
- post when balanced;
- inspect posted entries in read-only mode.

Posting uses the canonical Accounting domain and server repository. The page does not implement a competing double-entry posting engine.

Draft entries do not affect official reports.

Posted entries are read-only in the UI and remain protected by the domain/repository boundary.

## General Ledger UI

The Grand livre tab consumes the SPR-431 server-derived General Ledger report.

It supports:

- date range filtering;
- account filtering;
- opening balance;
- period movements;
- debit;
- credit;
- running balance;
- closing balance;
- traceability through journal entry number, journal code and line label.

Official ledger balances are not calculated in React.

## Trial Balance UI

The Balance tab consumes the SPR-431 server-derived Trial Balance report.

It displays:

- account;
- opening balance;
- period debit;
- period credit;
- closing debit;
- closing credit;
- global totals;
- reconciliation state.

The Balance derives from posted journal lines only.

## Module Activation

`finance.accounting` is now:

- `status: "alpha"`;
- `alphaReady: true`;
- visible;
- active in the default `alpha.crm-sales` Edition profile;
- routed to `/accounting`;
- grouped under Finance navigation.

Activation was changed only after the route, workspace, account UI, journal UI, manual entry flow, posting flow, General Ledger UI and Trial Balance UI were implemented and validated.

## Navigation

Finance navigation is provided through module metadata:

```text
Finance
  └── Comptabilité
```

The internal workspace tabs provide the operational sub-areas.

## Command Center / Unified Search

Command Center navigation support is implemented through existing module navigation metadata.

Users can find Comptabilité through keywords such as:

- finance;
- comptabilité;
- plan comptable;
- journaux;
- écritures;
- grand livre;
- balance.

Unified record search for accounts and journal entries is deferred to avoid expanding the sprint into a full search-provider implementation.

## Persistence / Migration

No Prisma schema change was required.

No migration was created.

SPR-432 uses the existing Accounting persistence API and repository.

One server-side hardening was added: UI-created Accounting records are scoped to the authenticated tenant/company on the server. React does not need to know or submit the authoritative `tenantCompanyId`.

## Medium Sprint Assessment

Was the medium sprint coherent? Yes. The sprint delivered one end-to-end capability instead of isolated screens.

Did scope remain manageable? Yes, because automatic posting, record search, statements and localization were explicitly deferred.

Did implementation quality remain comparable to smaller sprints? Yes. The implementation reused SPR-430/431 and added runtime validation instead of bypassing the accounting domain.

Were regressions easy to identify? Yes. Runtime validation immediately identified stale Alpha navigation assumptions.

Did Codex need shortcuts or architectural compromises? No. Finance activation happened through Module Registry and Edition Profiles, and reports remain server/domain-derived.

Should future BOSIACO work continue with this medium capability sprint size? Yes, when the scope is one coherent workflow with clear deferral rules. Avoid using medium sprints for multiple unrelated domains.

## Recommended Next Sprint

Recommended next direction: **Commercial Accounting Integration Readiness**.

Before automatic posting, BOSIACO should define explicit mapping rules from operational source documents to Accounting entries:

- Sales Invoice posting map;
- Sales Payment posting map;
- Procurement Supplier Invoice boundary;
- Inventory valuation boundary;
- reversal/correction strategy.

This should come before Financial Statements so reports are based on meaningful accounting activity beyond manual entries.
