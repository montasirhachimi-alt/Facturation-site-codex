# SPR-424 — Shipment & Delivery Foundation

## Summary

SPR-424 introduces the Shipment foundation as the logistics layer after posted Delivery Notes.

Shipment does not post stock. Inventory remains updated only by Delivery Notes. The Shipment workflow helps users organize transport, tracking and delivery status after the physical stock issue has already happened.

## Scope Delivered

- New Sales Shipment domain:
  - Shipment number
  - Delivery Note reference
  - Customer/company context
  - Sales Order reference
  - Carrier
  - Tracking number
  - Shipment date
  - Expected delivery
  - Status
  - Notes
  - Product lines and quantities copied from the posted Delivery Note
- New Shipment workspace at `/sales/shipments`.
- New Shipment details page at `/sales/shipments/[shipmentId]`.
- Creation from a posted Delivery Note through `/sales/shipments?deliveryNoteId=...`.
- Delivery Note details now exposes `Creer une expedition` when the Delivery Note is posted.
- Shipment dashboard section prepared for active Sales Operations profiles.
- Sales module metadata, routes, navigation and search provider include Shipments.

## Status Model

Supported statuses:

- Brouillon
- Pret
- Expedie
- En transit
- Livre
- Annule

Statuses are displayed with colored badges, and the details page includes a visible shipment lifecycle timeline.

## UX Decisions

- Shipment terminology uses logistics vocabulary, not stock posting vocabulary.
- The creation dialog clearly states that Shipment does not modify Inventory.
- Users only enter logistics fields when creating a Shipment from a Delivery Note:
  - Transporteur
  - Numero de suivi
  - Date d'expedition
  - Livraison prevue
  - Notes logistiques
- Products and quantities are auto-filled from the posted Delivery Note.
- Icon-only actions include tooltips, `title`, `aria-label` and visible focus states.
- Empty states explain the next action in French.
- Filters are explicit: statut, transporteur, client, date and search.

## Architecture

Created under:

```text
src/modules/sales/shipments/
```

The module follows the existing Sales module pattern:

- `shipment.types.ts`
- `shipment.constants.ts`
- `shipment.utils.ts`
- `shipment.service.ts`
- `shipment.store.ts`
- `ui/`

The service is local/session-scoped for this foundation. No Prisma model, migration, API route or persistence bridge was introduced in SPR-424.

## Inventory Boundary

Shipment never calls Inventory posting.

Inventory remains affected only by Delivery Note posting. Shipment stores logistics state and references the Delivery Note, Sales Order and Company context.

## Activation

`sales.shipments` is registered as an Alpha-capable Sales module and added to the internal `sales-operations` profile after `sales.delivery-notes`.

Suggested Sales Operations order:

1. Devis
2. Commandes clients
3. Bons de livraison
4. Expeditions
5. Factures
6. Paiements

The default `alpha.crm-sales` profile remains unchanged.

## Dashboard

The Shipment dashboard section exposes:

- Pretes a expedier
- En transit
- Livrees aujourd'hui
- En retard

It renders only when `sales.shipments` is active through module activation.

## Limitations

- Shipment persistence is not implemented in SPR-424.
- Carrier APIs are not implemented.
- Barcode labels are not implemented.
- GPS tracking is not implemented.
- Customer notifications are not implemented.
- Shipment status timestamps are represented by the current updated date only.
