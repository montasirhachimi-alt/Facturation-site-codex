# SPR-430 — Global Accounting Domain Foundation V1

Status: Completed
Date: 2026-08-17

## Objective

SPR-430 begins the BOSIACO Accounting domain by establishing a minimal, country-agnostic, tenant-scoped and double-entry-based Accounting Core.

This sprint does not deliver a Finance UI, automatic invoice posting, supplier invoices, VAT reporting, bank reconciliation, stock valuation or localization compliance.

- Legacy `PurchaseInvoice` and `PurchaseInvoiceLine` Prisma models.

- Active Sales `SalesInvoice`, `SalesInvoiceLine` and `SalesPayment` models.
- Planned hidden descriptors `finance.cash` and `finance.reports`.

## Double-Entry Invariant

For every posted entry:

```text
TOTAL DEBIT = TOTAL CREDIT
```

This is enforced in the domain boundary by:

- `validateJournalEntry()`
- `isJournalEntryBalanced()`
- `postJournalEntry()`
- `AccountingService.postEntry()`
- `postAccountingEntry()` in the repository layer

Unbalanced entries may exist as draft only. They cannot become posted.

## Amount Precision

The domain uses canonical decimal strings such as:

```text
1000.00
```

Domain calculations convert those strings to integer minor units internally, avoiding floating-point authority for debit/credit totals.

Prisma persists accounting amounts as `Decimal`.

## Posting Lifecycle

V1 lifecycle:

```text
draft -> posted
```

Rules:

- draft entries can be created and updated;
- posted entries are accounting history;
- posted entries cannot be silently modified through the draft persistence path;
- future corrections should use explicit reversal/correction mechanisms.

SPR-430 does not implement reversal workflows yet.

## Auditability Boundary

The V1 boundary is intentionally conservative:

- `persistAccountingJournalEntryDraft()` rejects modification of an existing posted entry;
- `AccountingService.updateDraftEntry()` rejects posted history;
- posted entries preserve `postedAt` and `postedBy`.

This prevents treating posted accounting history as ordinary mutable CRUD data.

## Tenant / Company Isolation

Isolation is enforced at multiple boundaries:

- Prisma models reference `Company` through `tenantCompanyId`;
- repositories call `requirePersistenceTenantScope()`;
- account and journal ownership is checked before persistence;
- journal entry lines cannot reference accounts from another tenant;
- journal entries cannot use journals from another tenant;
- runtime validation covers cross-tenant account misuse.

## Currency Readiness

SPR-430 preserves the distinction between:

```text
Company country
```

and:

```text
Functional / base currency
```

V1 stores:

- `functionalCurrency` on Journal Entry;
- optional `transactionCurrency`;
- optional `exchangeRate`;
- optional account-level currency readiness.

Not implemented:

- FX revaluation;
- exchange gains/losses;
- historical exchange-rate service;
- foreign-currency reconciliation;
- multi-currency reports.

## Localization Boundary

The Accounting Core is global and country-agnostic.

It does not hardcode:

- Moroccan PCG;
- Moroccan VAT rules;
- French or Spanish accounting rules;
- statutory reports;
- fiscal declarations.

Future localization packs can provide chart templates, tax definitions, fiscal conventions and statutory reporting without changing the core double-entry ledger model.
