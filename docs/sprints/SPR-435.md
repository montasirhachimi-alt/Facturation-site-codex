# SPR-435 — Accounting Corrections, Period Control & Auditability V1

Status: Completed
Date: 2026-08-18
Sprint type: Medium / Large Capability Sprint

## Executive Summary

SPR-435 makes BOSIACO Accounting safer to operate after financial statements.

Implemented capabilities:

- canonical reversal entries for posted Accounting history;
- durable original/reversal linkage;
- duplicate reversal prevention;
- mandatory correction reason;
- minimal tenant-scoped Accounting periods;
- OPEN/CLOSED posting-date control;
- period close and explicit reopen actions;
- commercial Sales source status detection after reversal;
- Finance UI controls for reversals and periods.

The canonical financial source of truth remains posted journal entries and lines.
No statutory closing, VAT localization, AP accounting, inventory valuation or retained-earnings transfer was added.

## Repository Reconciliation

Existing foundations before SPR-435:

- posted journal entries were protected from silent draft mutation;
- journal entries already carried `postedAt`, `postedBy`, `createdBy`, `updatedBy`, `sourceType` and `sourceId`;
- Sales invoice/payment posting already used durable source idempotency through `tenantCompanyId + sourceType + sourceId`;
- General Ledger, Trial Balance, Profit & Loss and Balance Sheet already derived from posted lines.

Missing foundations:

- no persisted Accounting period model;
- no original/reversal linkage;
- no canonical reversal construction helper;
- no server-side closed-period posting control;
- no visible Finance workflow for corrections.

## Correction Model

Posted history is never rewritten.

V1 correction flow:

```text
Original POSTED Entry
        ↓
Reversal POSTED Entry
```

The optional corrected replacement entry remains a manual Finance workflow for now. Users can create a new draft separately after reversing the incorrect entry.

## Reversal Construction

Reversal entries are created by a pure deterministic helper:

```text
for each original line:
  reversal.debitAmount  = original.creditAmount
  reversal.creditAmount = original.debitAmount
```

The reversal keeps:

- the original journal;
- the original tenant/company;
- the original functional currency;
- exact minor-unit values;
- line account identity;
- correction metadata in line metadata.

## Reversal Linkage

Persistent fields were added on `AccountingJournalEntry`:

- `reversalOfEntryId`;
- `correctedByEntryId`;
- `correctionReason`;
- `correctionType`.

The reversal also uses:

```text
sourceType = accounting.reversal
sourceId   = originalEntryId
```

This keeps the reversal explicit and queryable without relying on descriptions.

## Idempotency

Duplicate reversal is prevented by:

- repository lookup before creation;
- `AccountingJournalEntry.reversalOfEntryId` unique constraint;
- existing `tenantCompanyId + sourceType + sourceId` source idempotency.

A posted entry may have at most one canonical reversal through the V1 workflow.

## Source-Generated Entries

Sales invoice/payment entries remain source-linked.

After reversal:

- the original accounting entry remains visible;
- the reversal remains visible;
- the Sales source status becomes `reversed`;
- the UI no longer presents that source as simply `Comptabilisé`.

## Reposting Semantics

SPR-435 does not implement a full repost/amendment workflow.

The durable Sales source uniqueness remains intact. Once a source posting is reversed, re-posting that same source is rejected with an explicit message instead of silently creating a second live posting.

Future work may introduce a dedicated source accounting lifecycle if controlled reposting is required.

## Accounting Period Model

Added persistent `AccountingPeriod`:

- tenant/company;
- name;
- start date;
- end date;
- status;
- close/reopen audit metadata;
- creation/update audit metadata.

Statuses:

- `open`;
- `closed`.

Periods are tenant-scoped and validated against overlapping date ranges in the Accounting domain/repository layer.

## Period Lifecycle

V1 supports:

- create period;
- edit period metadata;
- close period;
- reopen period through an explicit action.

Reopening is intentionally supported as an explicit controlled action in Alpha because no statutory/legal close is claimed yet.

## Closed-Period Posting Rules

Closed periods block posting dates server-side.

Manual entries:

- draft creation/edit can remain possible;
- posting is rejected when `entryDate` falls inside a closed period.

Commercial postings:

- Sales invoice/payment accounting posting uses the same period check;
- no special bypass exists for commercial entries.

Reversals:

- original closed-period history is not mutated;
- reversal may be posted in an open period;
- reversal in a closed period is rejected.

## Report Effects

No report-specific correction math was added.

Reversals naturally flow through:

- General Ledger;
- Trial Balance;
- Profit & Loss;
- Balance Sheet;
- Finance Dashboard contribution.

If a reversal is posted in a later period, that later period carries the financial effect. Prior reports are not silently rewritten.

## Auditability

SPR-435 preserves:

- `createdAt`;
- `updatedAt`;
- `createdBy`;
- `updatedBy`;
- `postedAt`;
- `postedBy`;
- `closedAt`;
- `closedBy`;
- `reopenedAt`;
- `reopenedBy`;
- `sourceType`;
- `sourceId`;
- `reversalOfEntryId`;
- `correctionReason`;
- `correctionType`.

Actor identity uses the authenticated persistence scope when available.

## UI Changes

- `Périodes` tab;

- explicit close/reopen period actions;
- `Contrepasser` action for eligible posted entries;
- reversal confirmation dialog with date and reason;
- status labels for `Contrepassée` and `Contrepassation`;
- commercial source status `Contrepassé`.
